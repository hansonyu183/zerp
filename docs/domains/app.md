# APP 访问、会话与权限领域

## 1. 文档目的

本文定义 ZERP **APP（Application）** 领域的业务边界、数据模型、状态与安全规则，以及前后端职责。HTTP 路径和数据结构以根目录 OpenAPI 为准。

APP 使用固定领域标识 `app`。本文记录 OpenAPI 无法独立表达的认证、授权、事务、失效和交互语义，不维护第二套线协议。

## 2. 领域职责与边界

APP 负责：

- 用户身份认证和账号状态管理；
- 角色维护及用户与角色的关联；
- 后端 API 权限目录维护及角色授权；
- Cookie 会话的创建、恢复、续期和失效；
- CSRF 凭证签发与校验；
- 计算当前用户的最终 API 权限集合；
- 维护由代码或迁移注册的非敏感系统参数；
- 维护系统默认与业务归类两种导航模式，以及可编辑业务菜单模板；
- 记录认证、授权和管理操作审计事件。
- 接收登录用户反馈，并可靠发布为待人工审核的 GitHub Issue。

APP 不负责：

- 客户、供应商、产品等业务主数据；
- 组织、岗位和数据范围规则，除非后续以独立需求纳入；
- 前端组件路径和页面路由实现；
- 仅依靠前端菜单或按钮可见性实现安全控制。

## 3. 领域模型

### 3.1 核心实体

| 实体         | 建议表名                   | 说明                                                    |
| ------------ | -------------------------- | ------------------------------------------------------- |
| 用户         | `app_users`                | 可登录的身份主体，保存账号状态和密码摘要                |
| 用户资料     | `app_user_profiles`        | 用户的一对一扩展资料，当前保存私有配置的 HTTPS 头像地址 |
| 角色         | `app_roles`                | 可复用的权限集合                                        |
| 权限         | `app_permissions`          | 后端可调用 API 的目录项，路径是业务唯一标识             |
| 用户角色     | `app_user_roles`           | 用户与角色的多对多关联                                  |
| 角色权限     | `app_role_permissions`     | 角色与权限的多对多关联                                  |
| 会话         | `app_sessions`             | 服务端会话、到期和注销状态                              |
| 审计事件     | `app_audit_events`         | 登录、退出及授权变更的追加式记录                        |
| 用户反馈     | `app_feedback`             | 脱敏后的反馈内容、发布队列状态和 GitHub Issue 结果      |
| 反馈截图文件 | `app_feedback_files`       | 反馈专用私有截图、上传状态、归属和过期时间              |
| 反馈附件快照 | `app_feedback_attachments` | 已提交附件的非敏感元数据快照；保留历史 VOU 来源标记     |
| 系统参数     | `app_system_parameters`    | 代码或迁移注册的非敏感运行参数及其配置值、默认值        |
| 业务菜单项   | `app_business_menu_items`  | 业务归类模板中的分组、路由引用、顺序、显示和并发版本    |

关系如下：

```text
User ──< UserRole >── Role ──< RolePermission >── Permission
  │
  ├──── UserProfile
  │
  └──< Session
```

### 3.2 通用字段约定

除关联表外，领域表至少包含：

- `id`：稳定唯一标识，建议使用 UUID 或 ULID；
- `created_at`、`created_by`：创建审计信息；
- `updated_at`、`updated_by`：最后修改审计信息；
- `revision`：从 1 开始递增的乐观并发版本号。

数据库时间统一保存为 `timestamptz`，由服务端生成或读取数据库当前时间。客户端传入的创建人、修改人、审核人和时间一律忽略。

### 3.3 用户

`app_users` 至少包含：

| 字段                       | 约束               | 说明                                 |
| -------------------------- | ------------------ | ------------------------------------ |
| `id`                       | 主键               | 用户标识                             |
| `username`                 | 非空、规范化后唯一 | 登录名                               |
| `display_name`             | 非空               | 显示名称                             |
| `password_hash`            | 非空               | 强密码哈希摘要，不保存明文或可逆密文 |
| `status`                   | 非空               | `ENABLED` 或 `DISABLED`              |
| `failed_signin_count`      | 非空、默认 0       | 连续失败次数，供防暴力破解使用       |
| `locked_until`             | 可空               | 临时锁定截止时间                     |
| `password_changed_at`      | 非空               | 密码最后变更时间                     |
| `password_change_required` | 非空、默认 `true`  | 是否必须先修改初始密码               |
| `revision`                 | 非空               | 并发控制版本                         |

用户名入库和查询必须使用同一套规范化规则。是否区分大小写、允许字符、长度和锁定阈值应由配置或补充契约固定，不能在不同接口中使用不同规则。

管理员创建的普通用户默认启用并标记为必须修改初始密码。该标记为真时，登录响应和会话恢复必须向客户端返回受限会话状态，前后端都不得允许用户进入或调用普通业务功能；用户只能完成会话恢复、修改本人密码或安全退出。修改密码必须在同一事务中清除该标记并撤销该用户全部既有会话，用户随后使用新密码重新登录。

用户停用或密码变更后，既有会话必须立即或通过同一请求事务失效。

### 3.4 角色

`app_roles` 至少包含：

| 字段          | 约束                     | 说明                    |
| ------------- | ------------------------ | ----------------------- |
| `id`          | 主键                     | 角色标识                |
| `code`        | 非空、唯一、不可随意变更 | 稳定角色编码            |
| `name`        | 非空                     | 显示名称                |
| `description` | 可空                     | 角色说明                |
| `status`      | 非空                     | `ENABLED` 或 `DISABLED` |
| `revision`    | 非空                     | 并发控制版本            |

角色停用后不再参与权限并集计算。系统不得把角色名称当作接口授权依据。

角色代码 `superadmin` 是服务端保留的唯一通配角色。启用的 `superadmin` 不保存逐项角色权限关联，服务端在计算权限时将其展开为权限目录中全部 `ENABLED` API；客户端不能创建第二个 `superadmin`，也不能通过名称或自定义角色代码获得通配语义。

### 3.5 权限

`app_permissions` 至少包含：

| 字段          | 约束       | 说明                              |
| ------------- | ---------- | --------------------------------- |
| `id`          | 主键       | 权限标识                          |
| `path`        | 非空、唯一 | 标准 API 路径                     |
| `domain`      | 非空       | 领域标识，例如 `app`、`bob`       |
| `entity`      | 非空       | 实体标识，例如 `user`、`customer` |
| `action`      | 非空       | 动作标识，例如 `query`、`approve` |
| `description` | 可空       | 权限说明                          |
| `status`      | 非空       | `ENABLED` 或 `DISABLED`           |

权限路径必须由 `domain`、`entity`、`action` 规范化生成：

```text
/{domain}/{entity}/{action}
```

约束：

- 路径与三个拆分字段必须一致；
- 只允许小写字母、数字和单个连字符组成的段；
- 禁止空段、尾随斜杠、查询参数和 `*` 通配符；
- 权限目录以服务端已注册的受保护路由为来源，不接受前端创建任意路径；
- 路由下线时优先停用权限，保留历史授权与审计记录。

可在部署或受控管理命令中执行“路由目录同步”，但同步必须可审计，不得在普通请求中隐式创建权限。

### 3.6 关联表

`app_user_roles` 使用 `(user_id, role_id)` 唯一约束；`app_role_permissions` 使用 `(role_id, permission_id)` 唯一约束。两张表均保存 `created_at`、`created_by`。

系统内置固定用户 `system`（显示名“系统用户”）和固定角色 `system`（名称“系统角色”），用于归属系统自动生成的数据和自动执行的操作。该用户固定为停用状态，不能登录；该角色固定为启用状态且不授予任何 HTTP 权限。用户和角色均由迁移和服务端维护，不允许通过用户、角色管理接口创建同名主体、修改、启停或将系统角色授予其他用户。

关联删除表示撤销当前授权，不代表删除用户、角色、权限或审计历史。用户角色和角色权限的批量替换必须在单个事务中完成，避免出现部分授权状态。`superadmin` 是唯一例外：其有效权限由保留角色代码动态展开，`app_role_permissions` 中不得保存该角色的逐项关联。

### 3.7 会话

`app_sessions` 至少包含：

| 字段                           | 约束       | 说明                            |
| ------------------------------ | ---------- | ------------------------------- |
| `id`                           | 主键       | 内部会话标识                    |
| `user_id`                      | 外键、非空 | 所属用户                        |
| `token_hash`                   | 非空、唯一 | Cookie 中随机会话令牌的安全摘要 |
| `csrf_token_hash`              | 非空       | 当前 CSRF Token 的安全摘要      |
| `created_at`                   | 非空       | 创建时间                        |
| `last_seen_at`                 | 非空       | 最近有效访问时间                |
| `idle_expires_at`              | 非空       | 空闲到期时间                    |
| `absolute_expires_at`          | 非空       | 绝对到期时间                    |
| `revoked_at`、`revoked_reason` | 可空       | 注销或服务端失效信息            |

数据库不得保存或记录 Cookie 中的原始会话令牌。令牌必须由密码学安全随机源生成，比较摘要时避免产生可利用的时序差异。

会话过期策略、单用户最大会话数以及是否续期由部署配置确定；绝对到期时间不得被滑动续期突破。

### 3.8 系统参数

`app_system_parameters` 只保存由代码或迁移注册的参数；其中只有被注册流程显式标记为 `safe_to_expose=true` 的非敏感项才能进入通用查询、详情、保存和恢复默认接口，未标记项默认隐藏且按不存在处理。安全项至少包含参数键、名称、说明、值类型、配置值、默认值、是否可编辑、`revision`、更新时间和更新人。对 `RESTART_REQUIRED` 参数，还必须保存或可确定运行值与 `restartPending`，以区分已配置目标和当前运行实例采用的值。

参数键是不可由页面创建或修改的稳定标识。首版基础值类型只允许 `STRING`、`INTEGER`、`DECIMAL`、`BOOLEAN`。通用编辑仅适用于已显式注册参数专属约束的参数；约束至少能在基础类型之外完整判定默认值、既有配置值与新值是否有效。未注册充分约束的参数必须只读。注册参数或变更约束时，不得静默转换、重置或接受不满足新约束的默认值或既有配置值，必须先由受控注册流程处理不一致数据。

保存和恢复默认值均由后端按基础类型及已注册约束校验，并以 `revision` 乐观锁拒绝并发覆盖。密码、密钥、Token、Cookie、数据库连接和其他凭证继续使用环境变量或受控凭证存储，不得注册为系统参数。

参数生效模式的 wire value 与中文映射以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。领域语义区分立即采用、下次请求采用和受控重启确认三种方式。

`IMMEDIATE` 和 `NEXT_REQUEST` 的保存成功语义必须按各自名称明确表达，不产生待重启状态；`reset` 与 `save` 使用同一生效模式语义。对 `RESTART_REQUIRED`，每次产生新 `revision` 的保存或恢复默认都必须设置或保留 `restartPending`，即使新的配置文本恰好等于旧运行值，也不得用文本相等代替最新版本采用证明。页面不得执行重启。部署配置必须固定部署范围、当前实例标识和完整预期实例清单；每个服务实例启动时先把当前配置值及版本加载为本实例运行快照，再只能以自己的部署身份上报自己实际加载的版本，不接受 HTTP 或人工命令代报其他实例。首个上报事务固化该版本的预期实例清单，后续实例的清单不一致时启动失败。只有固定清单内全部实例都为同一最新版本完成自报时，事务才更新运行值并清除 `restartPending`；证明不完整、重复或陈旧时保留旧运行值和待重启状态。

`app.menu.mode` 是菜单服务专用参数，只允许 `DEFAULT` 或 `BUSINESS_TEMPLATE`。它在通用系统参数查询中可见但不可编辑，仍由菜单服务维护；通用 `save` 和 `reset` 必须拒绝修改该键。

### 3.9 菜单模板

菜单只控制导航的分组、顺序、显示名称、图标和启停，不改变任何后端授权。最终导航必须由模板路由与当前用户有效 API 权限取交集，直接访问页面和调用接口仍分别由前端精确权限检查及后端精确路径鉴权拒绝越权。

菜单模式的 wire value 以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。业务上只区分只读的项目默认菜单和由草稿独立发布的业务模板快照。

业务模板由彼此独立的**草稿**和**已发布快照**组成。两者各自保存完整菜单树、路由墓碑和独立 `revision`；树项至少包含 `id`、`parent_id`、`GROUP/ROUTE` 类型、层级、排序号、显示名称、图标、启用状态、路由项的 `route_key` 与 `permission_code`、更新时间和更新人。草稿是管理员编辑对象，已发布快照才是 `BUSINESS_TEMPLATE` 导航的唯一来源；`DEFAULT` 始终只读。初始系统必须同时有有效草稿和有效已发布初始模板，避免切换后没有可用模板。

APP 管理页面的当前路由目录以[前端路由](../../frontend/src/router/index.ts)为准。用户、角色、权限、系统参数和菜单均属于 APP 领域；“管理”只描述职责，不构成独立领域或 `admin` 路由命名空间。
| 菜单管理 | `app/menu` | `/app/menu` |

这些是浏览器页面路由，不改变 APP API 的 `POST /app/{entity}/{action}` 路径。页面目录切换不得保留旧 `admin/*` URL、`route_key`、redirect、fallback 或兼容层。实施时必须原子重写草稿和已发布快照中的正常路由和路由墓碑：保留分组、排序、启停和删除意图，并提升对应 `revision`；目录变化使 `catalogRevision` 改变，旧目录下加载的写入必须冲突并刷新。`route_path` 由当前目录派生，不作为模板独立保存字段。

业务模板规则：

- 最多只允许两级结构；一级可以是直接路由或分组，分组的二级只能是路由项，禁止循环或悬空父子关系；
- 工作台是唯一固定为一级直接路由的入口，不设置“工作台”分组或同名二级菜单，也不能在其他分组中重复放置；
- 路由项只引用服务端代码或迁移可验证的 `route_key`，地址、`route_key` 和权限代码不可由页面编辑；
- 同一路由可在不同分组或同组重复出现；
- `get` 返回 `catalogRevision`：它是当前完整注册菜单目录（包括路由标识、地址、显示名称、权限、默认菜单顺序等）的确定性指纹；
- 草稿保存、发布、模式切换和草稿恢复各自携带相应当前 `revision` 与 `catalogRevision`。服务端在事务中重新计算并校验目录证据；任一证据陈旧时以冲突拒绝，客户端刷新后由管理员重新决定，禁止自动合并；
- 保存只以当前草稿 `revision` 原子替换草稿树并提升草稿 `revision`；匹配目录版本时，草稿中省略目录路由才持久化为草稿墓碑；
- 发布以准确草稿 `revision` 与 `catalogRevision` 为输入，原子替换已发布快照并提升已发布 `revision`，但不切换菜单模式；
- `activate` 只在 `DEFAULT` 与最后已发布的 `BUSINESS_TEMPLATE` 之间切换，不发布草稿；`reset-business-template` 只把草稿恢复为初始模板并提升草稿 `revision`，恢复后必须再次发布才影响已发布快照或导航；
- 菜单管理路由至少保留一个启用实例，防止管理员失去恢复入口；
- 发布、模式切换和草稿恢复都需要二次确认并记录独立审计；
- 新注册且尚未存在于草稿的路由在读取时只追加到草稿“其他/待归类”，不改写管理员已有配置，也不得自动进入已发布快照；管理员整理并发布后才成为正式业务模板；
- 已下线路由不得继续导航；草稿保存和发布都必须按当前 `catalogRevision` 拒绝已下线或未注册路由；
- 默认初始导航先显示一级“工作台”路由，再显示销售、采购、生产、库存、出纳、资产、人事、会计、基础资料、辅助资料、业务流程、系统管理、其他/待归类分组。

## 4. 最终权限计算

普通角色的最终权限是以下集合的去重并集：

```text
有效用户
  → 有效的用户角色关联
  → ENABLED 角色
  → 有效的角色权限关联
  → ENABLED 权限
  → permission.path 去重、升序输出
```

若有效用户关联了启用的 `superadmin`，最终权限改为权限目录中全部 `ENABLED` 权限，并继续以完整 API 路径去重、升序输出。通配语义只存在于服务端，不在会话响应中返回 `"*"`；登录和会话恢复仍返回展开后的 `permissions: string[]`，因此权限停用会立即从管理员权限中消失。

每个受保护 API 请求必须校验：

1. 会话存在、未注销且未过期；
2. 用户仍为 `ENABLED`；
3. CSRF 校验通过；
4. 除本节明确列出的会话自助接口外，用户当前最终权限包含请求的精确路径；
5. 用例自身要求的数据范围和状态规则通过。

允许使用权限缓存，但必须具有可靠的版本号或失效机制，保证用户、角色、权限停用以及关联撤销能及时生效。不能只信任登录时写入会话或返回给前端的权限快照。

`/app/user/signin` 和 `/app/user/session` 是认证入口，不要求已有 API 权限；`signin` 不要求已有 CSRF Token。`session` 只能恢复已有 Cookie 会话并签发或返回当前 CSRF Token。

`/app/user/change-password` 和 `/app/user/signout` 是每个有效会话固有的本人自助能力，只要求有效会话和 CSRF，不进入 `app_permissions`，也不参与角色逐项授权。它们只能修改当前主体的密码或撤销当前会话，不能接受其他用户作为操作目标。

`password_change_required` 为真时，会话进入强制改密限制：除 `/app/user/session`、`/app/user/change-password` 和 `/app/user/signout` 外，后端拒绝该会话调用任何接口，包括通常允许登录用户使用的其他自助接口。前端权限数组、菜单或路由状态不能放宽该限制。

`/app/feedback/attachment-initiate`、`/app/feedback/attachment-remove`、`/app/feedback/create` 和 `/app/feedback/get` 是登录用户自助接口，只要求有效会话和 CSRF，不进入 `app_permissions`，也不参与角色逐项授权。该例外只允许操作当前主体的未提交附件、提交反馈和查询本人反馈，不能读取其他用户数据。

会话接口只返回用户资料、CSRF Token、API 权限数组、`passwordChangeRequired` 和 `passwordMinLength`。菜单树通过会话级 `/app/menu/get` 单独读取；后端只返回已注册路由键、固定地址及展示元数据，不得指定可执行的前端组件路径。前端仍由本地页面注册表把 `route_key` 解析为固定组件。

## 5. 动作语义

### 5.1 登录

请求和响应字段直接使用 OpenAPI 生成类型。

成功处理必须：

1. 规范化用户名并读取用户；
2. 使用固定成本流程校验密码，避免通过响应内容或耗时差异枚举用户；用户名格式不合法、用户不存在或命中不可登录的系统身份时，也必须使用与真实密码摘要同类的虚拟摘要执行一次密码校验，不能直接快速返回；
3. 校验用户状态和临时锁定状态；
4. 创建新会话并设置 Cookie；
5. 计算当前权限数组；
6. 记录成功审计事件。

Cookie 至少设置 `HttpOnly`、`Secure`、适当的 `SameSite`、受限的 `Path` 和明确的有效期。跨域部署时必须联合验证 Cookie、CORS 和 HTTPS 配置。

登录失败必须提供可行动但不泄露内部实现的原因：已存在且启用的账号密码错误时，返回“密码错误，剩余重试次数 N”；次数用尽时同时说明账号已临时锁定；已锁定账号说明稍后重试；已停用账号说明联系管理员。未知用户名继续使用“用户名或密码错误”，避免通过响应确认账号是否存在。数据库错误、权限装配错误和其他内部故障只记录到带请求编号的服务端日志，客户端统一显示服务暂时不可用，不返回 SQL、调用栈、内部组件名或原始异常。内部日志和审计事件可以记录受控原因，但不得记录密码、原始 Cookie 或 CSRF Token。

登录页及受保护页面跳转的前后端编排见[登录页用例](../use-cases/app/signin.md)。

### 5.2 恢复会话

请求与响应结构以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。

有效会话返回与登录相同的数据结构，并使用最新用户资料和最新权限计算结果。会话无效、用户停用或到期统一返回“未登录/会话失效”业务码，并清除失效 Cookie。

若采用 CSRF Token 轮换，接口必须原子更新会话中的摘要后再返回新 Token。

### 5.3 退出登录

该动作是有效会话固有的本人自助能力，不要求角色授予精确 API 权限；有效会话通过 CSRF 校验后撤销当前会话并清除 Cookie。对已注销、不存在或已自然到期且不再能引发服务端状态变更的会话，可清除 Cookie 并返回成功，以保证客户端清理流程幂等；有效会话的 CSRF 失败不能伪装为成功。

### 5.4 当前用户自助接口

当前用户资料动作读取或保存当前会话用户的非敏感资料；请求结构以 OpenAPI 为准。

`displayName` 去除首尾空白后必须为 1–128 个 Unicode 字符。`avatarUrl` 省略、为 `null`
或为空字符串时清除头像；非空时必须是不含用户凭证和 Fragment 的 HTTPS 绝对地址，最长 500 个字符。
保存不接受用户 ID、角色、状态、密码或客户端 `revision`，不会撤销现有会话；成功响应与空对象读取结构一致。
无实际变化时幂等返回且不增加 `revision`。实际修改在同一事务内更新显示名称、头像和审计事件，
审计只记录字段是否变化，不记录头像地址。

该接口只读取或修改当前登录用户，不返回角色、密码摘要、失败登录计数或会话信息。

修改密码动作使用 OpenAPI 定义的当前密码和新密码字段。

后端必须重新校验当前密码，新密码不得与当前密码相同。修改密码、清除 `password_change_required`、撤销该用户全部会话及成功审计事件必须在同一事务中完成；成功后清除当前 Cookie，客户端必须重新登录。该接口不接受用户 ID、密码摘要、`revision` 或任何管理员代改目标。

`profile` 要求有效会话、CSRF Token 和 `/app/user/profile` 精确权限。`change-password` 是每个有效会话固有的本人自助能力，只要求有效会话和 CSRF，不进入角色权限；强制改密受限会话仍可调用该动作。

### 5.5 用户反馈

`POST /app/feedback/attachment-initiate` 使用有效会话和 CSRF 创建反馈专用上传。

成功返回 `fileId`、15 分钟有效的一次性 `uploadUrl` 和 `expiresAt`。客户端以声明的
`Content-Type`、`Content-Length` 对 `uploadUrl` 执行 `PUT`，上传成功返回 204。
只允许 PNG、JPEG，每张 1 字节至 10 MiB；后端同时校验长度、SHA-256 和文件魔数。
每个用户最多保留 3 个未提交文件，滚动 24 小时最多初始化 60 次。
`POST /app/feedback/attachment-remove` 请求 `{"fileId":"01J..."}`，只能删除当前用户尚未提交的文件。

`submissionKey` 是客户端为一次反馈草稿生成的 16–64 位幂等键，同一用户重试时必须复用；相同键和相同内容返回首次提交结果，不重复创建反馈或占用限额，复用相同键提交不同内容则拒绝。`category` 只允许 `BUG`、`SUGGESTION`、`OTHER`；标题 1–120 个 Unicode 字符，正文 1–4000 个 Unicode 字符。`pagePath` 只能是不带查询串和 Fragment 的站内绝对路径；最多引用 3 个不重复的严格 ULID。附件必须来自上述反馈专用流程、归属当前用户且状态为 `READY`；VOU 附件 ID 不再接受。提交后保存文件和文件名、MIME、大小、SHA-256 快照，但不生成公开地址，也不把截图内容或地址写入 GitHub Issue。已上传但 24 小时内未提交的文件由清理任务删除；已提交截图私有长期保留，当前不提供 HTTP 查看或下载接口。

后端在持久化前清除常见令牌、Cookie、CSRF、密码赋值、JWT 和私钥内容。每个用户滚动 24 小时最多提交 20 条。

`POST /app/feedback/get` 请求 `{"feedbackId":"01J..."}`，只允许提交者查询，返回分类、标题、`PENDING | PUBLISHED | FAILED`、公开 Issue URL 和时间。内部 `PROCESSING` 对外仍显示 `PENDING`，他人查询与记录不存在使用相同错误。

反馈提交与 GitHub 发布解耦：只要数据库可用就必须先持久化并返回 `PENDING`，不能因当前环境未启用发布器而拒绝提交。启用发布器的环境再由数据库租约队列异步发布到配置的 GitHub 仓库。Issue 必须原子附带 `automation:blocked`，正文不包含用户身份、IP、UA 或凭证；只有人工审核并移除阻塞标签后，自动 Issue 处理任务才能领取。暂时性错误指数退避，最多 10 次；永久 GitHub 4xx 或重试耗尽进入 `FAILED`。

### 5.6 用户管理

用户管理动作、路径与数据结构以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。

创建用户时初始状态固定为 `ENABLED`，并设置必须修改初始密码；响应不得返回初始密码。管理员重置密码和账号恢复仍属于独立安全流程，不得复用普通 `save` 接口直接传递新密码。

`get` 必须返回用户当前关联角色及其状态，使停用但尚未解除关联的角色保持可见。`save` 只接受完整角色集合，集合必须非空且全部角色存在并启用；不得自动隐藏、删除或保留停用角色。操作人保存本人资料时，提交角色集合必须与数据库当前集合完全一致，后端拒绝通过用户管理增加或移除本人角色。系统内置用户继续拒绝读取以外的管理动作。

用户角色委派与角色管理共享同一个授权上限：普通操作者的授权上限是其事务时刻最终有效权限集合，持有启用 `superadmin` 的操作者才拥有通配委派身份。拥有全部当前有限权限的普通角色仍不是 `superadmin`，不能分配 `superadmin`，也不会自动获得未来新增权限。角色目录为当前操作者返回逐项 `assignable`；只有启用、非系统且权限不超过操作者授权上限的普通角色可分配，`superadmin` 仅对当前持有启用 `superadmin` 的操作者可分配。

读取用户详情时必须保留全部既有关联并返回每个角色的状态、类型与可分配结论，同时返回目标是否可维护以及角色集合是否可修改。目标当前启用角色的最终权限并集超过操作者授权上限、目标持有 `superadmin` 而操作者不是 `superadmin`，或目标为系统身份时，目标不可维护。操作者可以维护本人普通资料，但提交的角色集合必须与事务内当前集合完全相同。

创建用户和保存其他用户的完整角色集合都必须在授权更新锁内重新读取操作者身份、目标当前角色、请求角色状态及其最终权限并集。请求只能包含事务时刻可分配的启用角色；越权、上级目标、特殊身份和 `superadmin` 伪造必须以脱敏业务错误拒绝。用户资料、角色集合和审计仍在同一事务提交，失败不得留下部分变更。

`enable` 和 `disable` 均不得以系统内置用户或当前操作者本人为目标。停用用户必须在同一事务中撤销该用户全部会话；重新启用只恢复账号登录资格，保留原密码和 `password_change_required`，不得恢复任何旧会话或隐式执行密码重置。首版停用请求不保存操作原因，审计仍记录操作者、目标、状态变化、结果、时间和 `requestId`。

管理员重置密码是独立安全动作，不得复用 `save` 或本人 `change-password`。该动作只允许以启用状态的普通非本人用户为目标；停用用户、系统内置用户和当前操作者本人必须拒绝，且重置不得隐式改变账号状态。后端生成满足密码策略的随机临时密码，并在同一事务中保存其摘要、设置 `password_change_required`、撤销目标用户全部会话、增加 `revision` 和记录审计。临时密码不设置独立时间期限，在用户完成强制改密或管理员再次重置前保持为当前有效密码。事务提交成功后仅在该次响应中返回一次临时明文密码，服务端不保存可恢复明文，也不提供再次读取接口；密码不得进入审计或日志。该动作实施前必须先加入 OpenAPI 和权限目录。

### 5.7 角色管理

角色管理动作、路径与数据结构以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。

每条权限独立授权。菜单不依赖 `query` 权限，因此不得自动补授或强制依赖同实体的 `query`；页面是否能完成查询由其实际动作权限决定。

角色查询固定每页 20 条，按 `code`、`id` 升序稳定分页；只接受匹配编码或名称的关键词和 `ENABLED | DISABLED` 状态。查询和详情在事务时刻根据操作者最终有效权限、是否持有启用 `superadmin`、目标角色当前有效权限以及操作者是否持有目标角色，返回完整 `VIEW | EDIT | ENABLE | DISABLE` 动作集合和 `assignable`。`system` 与 `superadmin` 必须保持可见，但二者均不可编辑或启停；普通角色高于操作者授权上限或由操作者自己持有时同样不可维护。`VIEW` 只由精确 `get` 权限产生，其他动作分别要求其精确路径权限；前端不得自行从角色编码或本地权限推导服务端动作。

角色详情返回编码、名称、说明、状态、类型、完整权限资料、revision、创建和更新时间以及同一套动作与可分配结论。`superadmin` 的权限详情在读取时动态展开为全部启用权限，但数据库不保存逐项关联；普通有限权限集合无论当前是否恰好覆盖全部权限，都不得获得通配身份。

创建普通角色不接受客户端编码。后端在授权更新锁和同一事务中分配 `ROL-0001` 至 `ROL-9999` 的最小下一个顺序编码，新角色立即启用；既有编码保持不可变。名称去除首尾空白后按英文大小写不敏感规则唯一，新写入不得与任何既有规范化名称冲突，迁移不得重命名或合并既有歧义数据。编号耗尽、名称重复、权限缺失、权限停用或权限超过操作者授权上限都返回稳定且脱敏的业务错误。编码分配、名称检查、角色、完整权限集合和审计原子提交。

保存只允许修改普通角色去除首尾空白后的唯一名称、可选说明和完整权限集合；编码和状态不可通过保存改变。后端在授权更新锁内重新计算操作者授权上限、目标当前权限、操作者角色关联和请求结果，拒绝系统或超级管理员角色、操作者自持角色、当前目标或请求结果超过授权上限、revision 冲突以及移除最后有效授权管理员。目标原有关联的停用权限保持可见，但保存请求不能继续包含停用权限，必须由管理员明确移除。

启用和停用使用稳定角色 ID 与 revision，分别要求精确动作权限，并在授权更新锁内重新验证目标可维护性、操作者关联、当前状态和最后有效授权管理员保护。停用只改变角色状态，不删除角色权限或用户角色关联，也不撤销现有会话；从关联用户下一次受保护请求开始，该角色不再贡献权限。重新启用后，从下一次请求开始只恢复仍启用权限的贡献。状态变更记录操作者、目标、结果、时间和 request ID，首版不保存原因。

### 5.8 权限目录

权限目录动作、路径与数据结构以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。

权限目录页面严格只读，只提供目录查询和权限详情查询，不提供权限创建、同步、启用、停用或其他编辑能力。权限创建、路由目录同步以及权限启停由部署流程或权限来源领域的受控流程负责；页面不替代这些流程，也不把它们变成普通请求中的隐式行为。

权限详情中的“直接关联角色数”只统计 `app_role_permissions` 中对该权限的显式角色关联，且包含停用角色；不包含启用 `superadmin` 的动态通配结果。页面不展示具体角色名单、来源对象、跳转入口或生命周期审计，只展示权限的路径、领域、实体、动作、说明、状态和直接关联角色数。

### 5.9 系统参数

系统参数动作、路径与数据结构以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。

每个动作独立校验有效会话、CSRF 和对应精确路径权限；`get` 用于编辑前的新鲜详情读取，不是对列表值读取设置额外安全边界。页面不能创建、删除或修改参数键、名称、说明、类型、默认值、约束或生效模式。`save` 与 `reset` 不得处理 `app.menu.mode`，也不得把修改前后的参数值写入审计摘要。

### 5.10 菜单管理

菜单管理动作、路径与数据结构以 [OpenAPI APP Schema](../../contracts/openapi/schemas/app.yaml) 为准。

`get` 只要求有效会话与 CSRF，用于所有登录用户取得导航，不是逐项权限接口。其余四个接口进入权限目录并执行各自精确路径鉴权。保存、发布和恢复均不得信任客户端提交的路由地址或权限代码；服务端按已注册 `route_key` 重新装配只读字段。保存、发布、模式切换和恢复分别在单个事务中完成版本校验、状态写入和独立审计。

## 6. 管理接口通用规则

分页、过滤和排序字段使用 OpenAPI 生成类型。

并发写请求必须携带目标当前 `revision`。更新 SQL 同时匹配 `id` 和 `revision`，成功后将 `revision` 加一；未更新任何行时重新判断“不存在”或“数据冲突”，禁止后写静默覆盖先写。

所有 ID、状态、分页范围、字符串长度和关联对象都必须在进入核心用例前校验。客户端字段名、排序方向和过滤表达式不得直接拼接 SQL。

## 7. 事务与一致性

以下操作必须使用单个数据库事务：

- 创建用户及分配初始角色；
- 替换用户角色集合；
- 创建或修改角色及替换权限集合；
- 停用用户并撤销其会话；
- 修改密码并撤销旧会话；
- 管理员重置密码并撤销目标用户全部会话；
- 创建、轮换或撤销会话与写入对应关键审计事件。
- 创建反馈、附件元数据快照及滚动窗口限流判断。
- 修改或恢复系统参数及写入对应审计事件。
- 保存、恢复业务菜单树或切换菜单模式及写入对应审计事件。

授权关联变更成功提交后，权限缓存才能失效。若缓存失效失败，必须采用版本号校验或默认回源数据库，不能继续把旧权限作为有效授权。

新增领域权限的迁移只负责登记 `app_permissions`；不得再为 `superadmin` 逐项插入 `app_role_permissions`。普通角色仍通过显式关联授权。

## 8. 安全与审计

- 密码使用当前认可的自适应强哈希算法，并在配置中固定参数和升级策略；
- 登录接口实施速率限制、失败计数和必要的临时锁定；
- Cookie 会话令牌、CSRF Token、密码和密码摘要禁止进入响应日志；
- 除认证入口以及本文明确列出的本人自助接口外，所有业务 `POST` 请求同时校验会话、CSRF 和精确 API 权限；
- 管理员不能停用最后一个可执行核心授权管理的有效账号，具体防锁死规则在初始化方案中固定；
- 审计记录至少包含事件类型、操作者、目标、结果、时间、`requestId` 和必要的变更摘要；
- 审计摘要不得包含密码、令牌、Cookie 或完整敏感数据；
- 权限不足与未登录使用不同的稳定业务码；内部异常不暴露 SQL、堆栈和数据库对象名。

## 9. 测试验收

至少覆盖：

1. 登录成功、统一失败消息、锁定、停用账号和密码变更后的旧会话失效；
2. Cookie 属性、会话到期、注销幂等和 CSRF 校验/轮换；
3. 多角色权限去重并集，以及用户、角色、权限停用后的即时失效；
4. 精确路径鉴权，拒绝前缀、大小写变化和通配符匹配；
5. `superadmin` 无逐项关联仍获得全部启用权限，新增和停用权限能即时反映在展开后的登录权限数组；
6. 用户角色和角色权限批量替换的事务回滚；
7. 并发修改相同用户或角色时只允许一个版本成功；
8. 权限独立授权，菜单准入不依赖 `query`，页面动作仍按精确路径控制；
9. 所有管理接口均不返回或记录敏感字段；
10. 未登录、无权限、参数错误、数据冲突和内部异常映射到稳定业务错误类别。
11. 普通登录用户无需角色反馈权限即可提交和查询本人反馈，且不能查询他人反馈；
12. 反馈限流、附件归属、敏感信息清洗、发布租约、重试终态和 `automation:blocked` 标签可验证。

## 10. 已配置策略与待决事项

当前实现已经固定：

- 用户名在比较和保存前去除首尾空白并转为小写，长度为 3–64 个 Unicode 字符；
- 密码最小长度由 `APP_PASSWORD_MIN_LENGTH` 配置，默认 12、允许 8–128，实际密码最长 256 个字符，
  并且必须同时包含 ASCII 小写、大写、数字和符号；
- 登录和会话恢复响应返回当前生效的密码最小长度，供开户和本人改密界面使用同一策略边界；
- 连续失败锁定阈值和锁定时间分别由 `APP_SIGNIN_LOCK_THRESHOLD`、`APP_SIGNIN_LOCK_DURATION` 配置，
  默认 5 次和 15 分钟；进程内还按规范化用户名限制每分钟最多 30 次登录请求；
- 会话空闲和绝对有效期分别由 `APP_SESSION_IDLE_TIMEOUT`、`APP_SESSION_ABSOLUTE_TIMEOUT` 配置，
  默认 30 分钟和 12 小时；受保护请求延长空闲期限，但不得突破绝对期限。

仍待产品或安全方案明确：

- 用户名允许字符、国际化用户名及保留名称策略；
- 单用户最大并发会话数；
- 账号恢复流程；
- 是否引入组织、岗位、租户和数据范围授权；
- 权限路由目录的构建期生成、启动期校验或部署期同步方案；
- 审计数据保留期限和查询权限。

## 11. 前端职责与交互约束

本节保留前端页面、状态和交互层必须遵守的领域约束；HTTP 线协议以根目录 OpenAPI 为准。

### 工作台待办

工作台通过会话级 `POST /app/workbench/query` 聚合当前用户可处理的业务资料与业务单据。该接口不新增独立权限；后端必须从当前会话权限推导实体范围，客户端不得指定实体或动作集合。

- 资料草稿仅在同时拥有对应实体 `query` 与 `submit` 时进入“待核对”；待审核资料在拥有 `query` 且满足以下任一条件时进入“待批准”：拥有 `approve` 或 `reject` 且当前用户不是提交人，或拥有 `unsubmit`。
- 单据草稿在拥有 `query` 与 `check` 时进入“待核对”；已核对单据在拥有 `query` 且拥有 `approve` 或 `uncheck` 时进入“待批准”。`APPROVED` 是已批准并已入账的终态，不产生人工“待完成”任务。
- 聚合响应只返回列表摘要和当前会话可执行动作；详情仍必须通过对应 BOB/VOU `get` 接口读取，正向和反向处理仍调用对应领域动作接口。
- 列表按更新时间倒序进行服务端分页；关键词只匹配资料编码/名称或单据号/往来方。
- 资料和单据均可按实体类型与待办状态进行服务端筛选；客户端提交的实体筛选只用于缩小结果集，后端仍必须先按当前会话权限推导可见实体并取交集，不能将筛选值视为权限范围。

待办行的反向操作限定为仍处于待办状态的直接逆向流转：

- BOB `PENDING` 行在用户拥有该实体 `unsubmit` 权限时返回“撤回提交”；调用 `/bob/{entity}/unsubmit` 将版本退回 `DRAFT`，必须填写原因；
- VOU `CHECKED` 行在用户拥有该实体 `uncheck` 权限时返回“反核对”；调用 `/vou/{entity}/uncheck` 将单据退回 `DRAFT`，不要求原因；
- BOB `EFFECTIVE` 和 VOU `APPROVED` 不属于待办，不为提供 `unapprove` 而进入工作台；撤销批准和反批准继续在对应资料或单据页面执行。

反向动作和正向动作一样由后端根据行状态与当前权限写入 `availableActions`。前端不得仅根据状态展示反向按钮，也不得把“驳回”替代“撤回提交”：驳回是审核人带意见退回，撤回提交是具备独立权限的逆向动作，两者审计语义不同。

页面入口、页签状态和刷新编排见[工作台用例](../use-cases/app/workbench.md)。

### 11.1 动态菜单

#### 11.1.1 生成原则

主导航由 `POST /app/menu/get` 返回，服务端先选择当前菜单模式，再将菜单树与当前用户的有效权限取交集。`DEFAULT` 使用系统默认分组且只读；`BUSINESS_TEMPLATE` 只使用最后已发布快照，草稿永不直接进入导航。

本地页面注册表仍是前端组件加载器的唯一来源。后端只返回已注册的 `route_key`、显示信息和只读路由地址，不能指定组件路径或任意 URL。

```text
登录/恢复会话
    ↓
读取当前菜单模式、已发布快照和已注册 route_key 目录
    ↓
选择 DEFAULT 或最后已发布 BUSINESS_TEMPLATE 菜单树
    ↓
与当前会话 permissions 取交集
    ↓
返回一级直接路由、分组、顺序、显示信息和只读路由地址
    ↓
已注册页面加载业务组件，未注册页面加载“开发中...”占位组件
    ↓
注册为 AppLayout 子路由并在业务菜单中显示
```

#### 11.1.2 菜单准入权限

业务路由只要匹配某个实体的任一有效 API 权限即可进入导航：

```text
/{domain}/{entity}/{action}
```

例如，权限数组包含：

```text
/bob/customer/create
/bob/supplier/approve
```

菜单中显示：

```text
业务对象
└── 客户
└── 供应商
```

菜单不要求 `query` 权限，也不以本地是否已经注册业务组件作为显示条件。系统管理路由使用各入口的精确只读或管理权限。菜单管理入口只要用户拥有 `save-business-template`、`publish-business-template`、`activate` 或 `reset-business-template` 任一菜单写权限即可显示，且草稿与已发布快照中均必须保留一个启用的菜单管理入口。页面内按钮分别按其精确权限判断，后端业务鉴权不因菜单配置而改变。

#### 11.1.3 本地页面注册表

权限数组只描述“允许调用哪些 API”，不包含可由后端任意指定的前端组件路径。页面组件加载器由前端本地注册表维护，例如：

```ts
{
  domain: 'bob',
  domainTitle: '业务对象',
  entity: 'customer',
  entityTitle: '客户',
  icon: 'mdi-account-group',
  order: 10,
  component: () => import('@/pages/bob/customer/Customer.vue'),
}
```

约束如下：

- 后端权限不能指定或加载任意前端组件。
- 本地已注册的实体使用注册表中的组件；未注册实体加载统一的“开发中...”占位组件。
- 用户没有某实体的任何权限时，不显示菜单，也不注册对应动态路由。
- 菜单点击后由 `AppLayout` 的 `<router-view>` 加载对应业务实体组件。
- 页面内按钮根据完整的动作权限判断是否显示或可用。
- 用户直接访问无权限路由时，前端显示无权限结果；后端仍必须拒绝相关 API 调用。
- 菜单显示名称、图标、分组、顺序和启停由选中的菜单树决定；这些字段不授予任何 API 权限。
- 新注册但尚未保存到草稿的路由由服务端只追加到草稿“其他/待归类”，不得覆盖管理员已保存的项目或自动进入已发布快照；已下线路由不得继续导航。
- APP 管理页面是静态本地路由；其 `route_key` 与 `route_path` 必须采用[菜单模板](#39-菜单模板)规定的 canonical 集合，不能由动态页面注册或旧 `admin/*` 路由补偿。

菜单发布、模式切换或已发布模板更新不主动推送到其他在线用户，也不撤销其会话。成功响应后当前管理员刷新自己的导航；其他用户在刷新页面、新开页面或恢复现有会话时重新读取菜单并获得最新已发布菜单，无需退出重登。当前已打开页面不强制跳转，直接路由和 API 权限继续独立鉴权。

#### 11.1.4 权限判断

前端提供统一判断函数：

```ts
can('/bob/customer/create')
can('/bob/customer/approve')
```

禁止页面自行使用字符串模糊匹配、前缀匹配或角色名称判断权限。

### 11.5 权限变更与会话一致性

- 用户角色或角色权限变更后，后端必须确保后续请求使用最新权限。
- 前端的权限数组用于交互控制，不得作为后端继续授权的缓存依据。
- 为及时刷新菜单，后端可以使相关用户会话失效，或通过权限版本号通知前端重新调用 `user.session`。
- 权限被撤销后，即使旧页面仍在显示，后端也必须立即拒绝无权限 API 请求。

### 11.6 与其他领域的关系

- APP 为 BOB 及其他业务领域提供用户身份和 API 权限判断。
- 其他领域只声明自身 API 所需的权限，不自行维护角色体系。
- APP 不根据角色名称生成菜单；菜单始终根据最终 API 权限数组生成。
- 业务领域的创建、编辑、提交、审核等动作分别对应独立 API 权限。
