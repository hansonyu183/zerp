# APP 访问、会话与权限领域

## 1. 文档目的

本文定义 ZERP **APP（Application）** 领域的业务边界、数据模型、状态与安全规则。HTTP 路径和数据结构由可执行 Hono/Zod 路由生成。

APP 使用固定领域标识 `app`。本文记录 OpenAPI 无法独立表达的认证、授权、事务、失效和业务协作语义，不维护第二套线协议。

本文的 APP 业务规则约束当前 Hono 运行时；涉及本地 Draft、Submission、shared TypeScript model 或 Workbench 的段落遵循 [Approval](approval.md) 的当前语义，临时输入不持久化。

## 2. 领域职责与边界

APP 负责：

- 用户身份认证和账号状态管理；
- 角色维护及用户与角色的关联；
- 后端 API 权限目录维护及角色授权；
- Cookie 会话的创建、恢复、续期和失效；
- CSRF 凭证签发与校验；
- 计算当前用户的最终 API 权限集合；
- 维护由代码或数据库基线注册的非敏感系统参数；
- 计算当前用户的精确 API 路径，供 Session Context 作为 Navigation Resource 的唯一输入；
- 记录认证、授权和管理操作审计事件。

APP 不负责：

- 客户、供应商、产品等业务主数据；
- 组织、岗位和数据范围规则，除非后续以独立需求纳入；
- 前端组件、页面路由、导航分组或导航显示名称；
- 菜单模板、菜单 API、菜单存储或菜单事务；
- 仅依靠前端菜单或按钮可见性实现安全控制。

## 3. 领域模型

### 3.1 核心实体

| 实体     | 建议表名                | 说明                                                    |
| -------- | ----------------------- | ------------------------------------------------------- |
| 用户     | `app_users`             | 可登录的身份主体，保存账号状态和密码摘要                |
| 用户资料 | `app_user_profiles`     | 用户的一对一扩展资料，当前保存私有配置的 HTTPS 头像地址 |
| 角色     | `app_roles`             | 可复用的权限集合                                        |
| 权限     | `app_permissions`       | 后端可调用 API 的目录项，路径是业务唯一标识             |
| 用户角色 | `app_user_roles`        | 用户与角色的多对多关联                                  |
| 角色权限 | `app_role_permissions`  | 角色与权限的多对多关联                                  |
| 会话     | `app_sessions`          | 服务端会话、到期和注销状态                              |
| 审计事件 | `app_audit_events`      | 登录、退出及授权变更的追加式记录                        |
| 系统参数 | `app_system_parameters` | 代码或数据库基线注册的非敏感运行参数及其配置值、默认值  |

关系如下：

```text
User ──< UserRole >── Role ──< RolePermission >── Permission
  │
  ├──── UserProfile
  │
  └──< Session
```

### 3.2 通用字段约定

除关联表外，领域表至少包含：

- `id`：稳定唯一标识，建议使用 UUID 或 ULID；
- `created_at`、`created_by`：创建审计信息；
- `updated_at`、`updated_by`：最后修改审计信息；
- `revision`：从 1 开始递增的乐观并发版本号。

数据库时间统一保存为 `timestamptz`，由服务端生成或读取数据库当前时间。客户端传入的创建人、修改人、审核人和时间一律忽略。

### 3.3 用户

`app_users` 至少包含：

| 字段                       | 约束               | 说明                                 |
| -------------------------- | ------------------ | ------------------------------------ |
| `id`                       | 主键               | 用户标识                             |
| `username`                 | 非空、规范化后唯一 | 登录名                               |
| `display_name`             | 非空               | 显示名称                             |
| `py`                       | 非空               | 服务端按名称维护的小写无声调拼音     |
| `password_hash`            | 非空               | 强密码哈希摘要，不保存明文或可逆密文 |
| `status`                   | 非空               | `ENABLED` 或 `DISABLED`              |
| `failed_signin_count`      | 非空、默认 0       | 连续失败次数，供防暴力破解使用       |
| `locked_until`             | 可空               | 临时锁定截止时间                     |
| `password_changed_at`      | 非空               | 密码最后变更时间                     |
| `password_change_required` | 非空、默认 `true`  | 是否必须先修改初始密码               |
| `revision`                 | 非空               | 并发控制版本                         |

用户名入库和查询必须使用同一套规范化规则。Session 和用户管理契约以 `code` 表达这一登录身份，但不建立第二套用户事实。是否区分大小写、允许字符、长度和锁定阈值应由配置或补充契约固定，不能在不同接口中使用不同规则。

用户管理的原生业务事实为稳定身份、账号编码、名称、拼音和启用标记；物理 `username`、`display_name`、`status` 列仍各自只有一套事实，不暴露同义响应别名。所有创建和改名入口（包括 Session 本人保存、管理员保存及受控初始化）使用同一成熟拼音实现生成小写无声调拼音；拼音不是客户端输入，不用空字符串伪造支持。拼音随创建或改名在应用事务内维护，不引入数据库函数或触发器。

管理员创建的普通用户默认启用并标记为必须修改初始密码。该标记为真时，登录响应和会话恢复必须向客户端返回受限会话状态，前后端都不得允许用户进入或调用普通业务功能；用户只能完成会话恢复、修改本人密码或安全退出。修改密码必须在同一事务中清除该标记并撤销该用户全部既有会话，用户随后使用新密码重新登录。

用户停用或密码变更后，既有会话必须立即或通过同一请求事务失效。

### 3.4 角色

`app_roles` 至少包含：

| 字段          | 约束                     | 说明                    |
| ------------- | ------------------------ | ----------------------- |
| `id`          | 主键                     | 角色标识                |
| `code`        | 非空、唯一、不可随意变更 | 稳定角色编码            |
| `name`        | 非空                     | 显示名称                |
| `description` | 可空                     | 角色说明                |
| `status`      | 非空                     | `ENABLED` 或 `DISABLED` |
| `revision`    | 非空                     | 并发控制版本            |

角色停用后不再参与权限并集计算。系统不得把角色名称当作接口授权依据。

角色代码 `superadmin` 是服务端保留的唯一通配角色。启用的 `superadmin` 不保存逐项角色权限关联，服务端在计算权限时将其展开为权限目录中全部 `ENABLED` API；客户端不能创建第二个 `superadmin`，也不能通过名称或自定义角色代码获得通配语义。

### 3.5 权限

`app_permissions` 至少包含：

| 字段          | 约束       | 说明                              |
| ------------- | ---------- | --------------------------------- |
| `id`          | 主键       | 权限标识                          |
| `path`        | 非空、唯一 | 标准 API 路径                     |
| `domain`      | 非空       | 领域标识，例如 `app`、`bob`       |
| `entity`      | 非空       | 实体标识，例如 `user`、`customer` |
| `action`      | 非空       | 动作标识，例如 `query`、`approve` |
| `description` | 可空       | 权限说明                          |
| `status`      | 非空       | `ENABLED` 或 `DISABLED`           |

权限路径必须由 `domain`、`entity`、`action` 规范化生成：

```text
/{domain}/{entity}/{action}
```

约束：

- 路径与三个拆分字段必须一致；
- 只允许小写字母、数字和单个连字符组成的段；
- 禁止空段、尾随斜杠、查询参数和 `*` 通配符；
- 权限目录以服务端已注册的受保护路由为来源，不接受前端创建任意路径；
- 暂时停用的资源停用其权限并保留授权关系；完整删除机制时，受控目录同步同时删除其权限及角色授权关联，保留独立审计和其他资源的精确授权。菜单模板属于完整删除的机制。

权限目录的登记与更新属于受控部署流程；普通请求不得隐式创建、启停或修改权限。

### 3.6 关联表

`app_user_roles` 使用 `(user_id, role_id)` 唯一约束；`app_role_permissions` 使用 `(role_id, permission_id)` 唯一约束。两张表均保存 `created_at`、`created_by`。

系统内置固定用户 `system`（显示名“系统用户”）和固定角色 `system`（名称“系统角色”），用于归属系统自动生成的数据和自动执行的操作。该用户固定为停用状态，不能登录；该角色固定为启用状态且不授予任何 HTTP 权限。用户和角色均由数据库基线和服务端维护，不允许通过用户、角色管理接口创建同名主体、修改、启停或将系统角色授予其他用户。

关联删除表示撤销当前授权，不代表删除用户、角色、权限或审计历史。用户角色和角色权限的批量替换必须在单个事务中完成，避免出现部分授权状态。`superadmin` 是唯一例外：其有效权限由保留角色代码动态展开，`app_role_permissions` 中不得保存该角色的逐项关联。

### 3.7 会话

`app_sessions` 至少包含：

| 字段                           | 约束       | 说明                            |
| ------------------------------ | ---------- | ------------------------------- |
| `id`                           | 主键       | 内部会话标识                    |
| `user_id`                      | 外键、非空 | 所属用户                        |
| `token_hash`                   | 非空、唯一 | Cookie 中随机会话令牌的安全摘要 |
| `csrf_token_hash`              | 非空       | 当前 CSRF Token 的安全摘要      |
| `created_at`                   | 非空       | 创建时间                        |
| `last_seen_at`                 | 非空       | 最近有效访问时间                |
| `idle_expires_at`              | 非空       | 空闲到期时间                    |
| `absolute_expires_at`          | 非空       | 绝对到期时间                    |
| `revoked_at`、`revoked_reason` | 可空       | 注销或服务端失效信息            |

数据库不得保存或记录 Cookie 中的原始会话令牌。令牌必须由密码学安全随机源生成，比较摘要时避免产生可利用的时序差异。

会话过期策略、单用户最大会话数以及是否续期由部署配置确定；绝对到期时间不得被滑动续期突破。

### 3.8 系统参数

`app_system_parameters` 只保存由代码或 baseline 注册、允许管理员查看的非敏感参数。字段只包含参数键、名称、说明、值类型、配置值、默认值、是否可编辑、约束和 `revision`；所有登记项都进入通用查询、详情、保存和恢复默认接口，不再维护第二层暴露标志。密码、密钥、Token、Cookie、数据库连接和其他凭证不得登记为系统参数。

参数键是不可由页面创建或修改的稳定标识。首版基础值类型只允许 `STRING`、`INTEGER`、`DECIMAL`、`BOOLEAN`。通用编辑仅适用于已显式注册参数专属约束的参数；约束至少能在基础类型之外完整判定默认值、既有配置值与新值是否有效。未注册充分约束的参数必须只读。注册参数或变更约束时，不得静默转换、重置或接受不满足新约束的默认值或既有配置值，必须先由受控注册流程处理不一致数据。

保存和恢复默认值均由后端按基础类型及已注册约束校验，并以 `revision` 乐观锁拒绝并发覆盖。

`app.enterprise-name` 是当前使用单位的企业名称，默认值为“ZERP 演示企业”，只用于登录页和登录后顶栏展示。它不是业务档案、经营主体或产品名，也不改变侧栏、面包屑和浏览器标题中的 `ZERP`。

保存成功表示配置值已经写入数据库并可由参数所属代码读取；部署实例是否已经加载配置属于部署系统职责。当前没有真实参数要求由 ERP 跟踪重启采用状态，因此不保存运行值、待重启标志、部署范围、实例清单或采用证明，也不因外部实例状态阻塞 ERP 启动。

### 3.9 导航资源

Navigation Resource 只从当前 Session Context 的非 Session `apiPaths` 得出。一个合法的精确业务路径按其 `domain/entity` 归属同一资源，资源内任一动作路径都足以产生入口；资源按 `domain/entity` 去重并按领域分组。`session` 路径绝不产生业务入口。

导航不得与 `query` 权限、页面登记、BusinessRegistry、被替代的路由目录或任意前缀匹配求交集。只有 `create` 的使用者仍可看到资源入口，但页面不得因此发送查询；未登记资源显示明确的尚未实现状态，不伪造空列表、被替代页面或无权限。缺少资源的直达地址不挂载业务功能或发起业务请求。

已知 `domain/entity` 使用统一中文资源名称；尚无展示名称的遗留资源必须显示其资源标识和待配置说明。前端可以用固定映射呈现名称和分组，但不能以 `hiddenDomains`、`showInMenu`、无实现即隐藏或可编辑菜单模板过滤已授权资源。

Navigation Entry 只是前端展示与页面装配的输入。它不授予权限、不替代受保护请求的精确路径校验，也不保存菜单树、分组、排序、图标、启停、路由目录或菜单 `revision`。APP 不提供菜单读取、保存、模式切换或恢复接口；启动不执行菜单同步。

## 4. 最终权限计算

普通角色的最终权限是以下集合的去重并集：

```text
有效用户
  → 有效的用户角色关联
  → ENABLED 角色
  → 有效的角色权限关联
  → ENABLED 权限
  → permission.path 去重、升序输出
```

若有效用户关联了启用的 `superadmin`，最终权限改为权限目录中全部 `ENABLED` 权限，并继续以完整 API 路径去重、升序输出。通配语义只存在于服务端，不在会话响应中返回 `"*"`；登录和会话恢复返回展开后的 `apiPaths: string[]`，因此权限停用会立即从管理员权限中消失。

每个受保护 API 请求必须校验：

1. 会话存在、未注销且未过期；
2. 用户仍为 `ENABLED`；
3. CSRF 校验通过；
4. 除本节明确列出的会话自助接口外，用户当前最终权限包含请求的精确路径；
5. 用例自身要求的数据范围和状态规则通过。

允许使用权限缓存，但必须具有可靠的版本号或失效机制，保证用户、角色、权限停用以及关联撤销能及时生效。不能只信任登录时写入会话或返回给前端的权限快照。

`/session/auth/signin` 是公开认证入口，不要求已有会话、API 权限或 CSRF Token。`/session/auth/restore` 只恢复已有 Cookie 会话并重新签发该会话固定的 CSRF Token，因此要求有效 Cookie 会话，但不要求客户端先持有旧 CSRF Token。同一 Cookie 会话在多个标签页或重复恢复时必须得到同一个 CSRF Token，不得因某个标签页恢复会话而使其他标签页立即失效。

`/session/user/get`、`/session/user/save`、`/session/user/change-password` 和 `/session/auth/signout` 是每个有效会话固有的本人自助能力，只要求有效会话和 CSRF，不进入 `app_permissions`，也不参与角色逐项授权。它们只能读取或修改当前主体、修改当前主体的密码或撤销当前会话，不能接受其他用户作为操作目标。

所有受保护路由只使用一套 HTTP 鉴权管线。`RequireSession()` 统一读取会话 Cookie、校验会话和用户状态、执行适用的 CSRF 与强制改密限制、续期空闲时间、注入当前主体，并在未认证时清除失效 Cookie；`RequirePermission(path)` 在同一次 `RequireSession()` 结果上追加精确路径权限检查。APP、BOB、VOU、ACC、AUX、WFL 和 RPT 不得各自读取 Cookie、重复实现会话校验或再建第二套完整鉴权。

`password_change_required` 为真时，会话进入强制改密限制：除 `/session/auth/restore`、`/session/user/change-password` 和 `/session/auth/signout` 外，后端拒绝该会话调用任何接口，包括通常允许登录用户使用的其他自助接口。前端权限数组、菜单或路由状态不能放宽该限制。

登录和会话恢复只返回唯一的会话上下文：`user` 的 `id`、`code`、`name`、去重展开的 `apiPaths`、`csrfToken`、`passwordChangeRequired` 和 `passwordMinLength`。它们不得返回通配符、`permissions`、`username`、`displayName` 或 `status` 别名。本人额外的非敏感资料只由 `/session/user/get` 返回。前端仅从这个 `apiPaths` 集合装配 Navigation Resource，不读取独立菜单树或菜单接口。

## 5. 动作语义

### 5.1 登录

请求和响应字段直接使用 OpenAPI 生成类型。

成功处理必须：

1. 规范化账号编码并读取用户；
2. 使用固定成本流程校验密码，避免通过响应内容或耗时差异枚举用户；账号编码格式不合法、用户不存在或命中不可登录的系统身份时，也必须使用与真实密码摘要同类的虚拟摘要执行一次密码校验，不能直接快速返回；
3. 校验用户状态和临时锁定状态；
4. 创建新会话并设置 Cookie；
5. 计算当前权限数组；
6. 记录成功审计事件。

Cookie 至少设置 `HttpOnly`、`Secure`、适当的 `SameSite`、受限的 `Path` 和明确的有效期。跨域部署时必须联合验证 Cookie、CORS 和 HTTPS 配置。

登录失败必须提供可行动但不泄露内部实现的原因：已存在且启用的账号密码错误时，返回“密码错误，剩余重试次数 N”；次数用尽时同时说明账号已临时锁定；已锁定账号说明稍后重试；已停用账号说明联系管理员。未知账号编码继续使用“账号或密码错误”，避免通过响应确认账号是否存在。数据库错误、权限装配错误和其他内部故障只记录到带请求编号的服务端日志，客户端统一显示服务暂时不可用，不返回 SQL、调用栈、内部组件名或原始异常。内部日志和审计事件可以记录受控原因，但不得记录密码、原始 Cookie 或 CSRF Token。

登录页及受保护页面跳转由 target SPA 的会话状态统一编排。

### 5.2 恢复会话

请求与响应结构以 Hono 生成契约为准。

有效会话返回与登录相同的数据结构，并使用最新用户资料和最新权限计算结果。会话无效、用户停用或到期统一返回“未登录/会话失效”业务码，并清除失效 Cookie。

CSRF Token 按 Cookie 会话固定，并由服务端从随机会话令牌单向派生；会话恢复重新签发同一个 Token，同时续期空闲时间。新登录创建新会话令牌，因此仍会得到不同的 CSRF Token；服务端只保存摘要，不保存或记录原始 Token。

### 5.3 退出登录

`/session/auth/signout` 是有效会话固有的本人自助能力，不要求角色授予精确 API 权限；有效会话通过 CSRF 校验后撤销当前会话并清除 Cookie。已注销、不存在或已自然到期的会话按未认证处理并清除 Cookie；有效会话的 CSRF 失败不能伪装为成功。

### 5.4 当前用户自助接口

`/session/user/get` 和 `/session/user/save` 读取或保存当前会话用户的非敏感资料；请求结构以 Hono 生成契约为准。

`name` 去除首尾空白后必须为 1–128 个 Unicode 字符。`avatarUrl` 省略、为 `null`
或为空字符串时清除头像；非空时必须是不含用户凭证和 Fragment 的 HTTPS 绝对地址，最长 500 个字符。
保存不接受用户 ID、账号编码、角色、状态、密码或客户端 `revision`，不会撤销现有会话；成功响应与空对象读取结构一致。
无实际变化时幂等返回且不增加 `revision`。实际修改在同一事务内更新用户名称、头像和审计事件，
审计只记录字段是否变化，不记录头像地址。

该接口只读取或修改当前登录用户，不返回角色、密码摘要、失败登录计数或会话信息。

`/session/user/change-password` 使用 Hono 生成契约定义的当前密码和新密码字段。

后端必须重新校验当前密码，新密码不得与当前密码相同。修改密码、清除 `password_change_required`、撤销该用户全部会话及成功审计事件必须在同一事务中完成；成功后清除当前 Cookie，客户端必须重新登录。该接口不接受用户 ID、密码摘要、`revision` 或任何管理员代改目标。

`get`、`save` 和 `change-password` 都是每个有效会话固有的本人自助能力，只要求有效会话和 CSRF，不进入角色权限；强制改密受限会话只能使用 `restore`、`change-password` 和 `signout`，不能使用 `get` 或 `save`。

### 5.5 用户管理

用户管理动作、路径与数据结构以 Hono 生成契约为准。

查询在完整服务端用户集合上对账号编码、拼音、名称进行 OR 包含匹配，按账号编码、稳定 ID 升序分页，每页固定 20 条。输入关键词只参与文本匹配，不解释为通配查询语法。用户列表不提供旧状态筛选或更新时间展示。具体字段以可执行 [用户契约](../../apps/api/src/app/contract.ts) 为准。

创建用户时初始状态固定为启用，并设置必须修改初始密码；响应不得返回初始密码。管理员重置密码和账号恢复仍属于独立安全流程，不得复用普通 `save` 接口直接传递新密码。

用户管理保存只修改名称和完整角色集合，不修改账号编码、密码或启用状态。读取与写入携带的并发 revision 保持十进制字符串，不能经过 Number 转换。查询和详情返回服务端对象动作资格；执行仍在服务拥有的同一事务重新检查授权上限、目标与角色事实以及最后有效授权管理员保护。

`get` 必须返回用户当前关联角色及其状态，使停用但尚未解除关联的角色保持可见。`save` 只接受完整角色集合，集合必须非空且全部角色存在并启用；不得自动隐藏、删除或保留停用角色。操作人保存本人资料时，提交角色集合必须与数据库当前集合完全一致，后端拒绝通过用户管理增加或移除本人角色。系统内置用户继续拒绝读取以外的管理动作。

用户角色委派与角色管理共享同一个授权上限：普通操作者的授权上限是其事务时刻最终有效权限集合，持有启用 `superadmin` 的操作者才拥有通配委派身份。拥有全部当前有限权限的普通角色仍不是 `superadmin`，不能分配 `superadmin`，也不会自动获得未来新增权限。角色目录为当前操作者返回逐项 `assignable`；只有启用、非系统且权限不超过操作者授权上限的普通角色可分配，`superadmin` 仅对当前持有启用 `superadmin` 的操作者可分配。

读取用户详情时必须保留全部既有关联并返回每个角色的状态、类型与可分配结论，同时返回目标是否可维护以及角色集合是否可修改。目标当前启用角色的最终权限并集超过操作者授权上限、目标持有 `superadmin` 而操作者不是 `superadmin`，或目标为系统身份时，目标不可维护。操作者可以维护本人普通资料，但提交的角色集合必须与事务内当前集合完全相同。

创建用户和保存其他用户的完整角色集合都必须在授权更新锁内重新读取操作者身份、目标当前角色、请求角色状态及其最终权限并集。请求只能包含事务时刻可分配的启用角色；越权、上级目标、特殊身份和 `superadmin` 伪造必须以脱敏业务错误拒绝。用户资料、角色集合和审计仍在同一事务提交，失败不得留下部分变更。

`enable` 和 `disable` 均不得以系统内置用户或当前操作者本人为目标。停用用户必须在同一事务中撤销该用户全部会话；重新启用只恢复账号登录资格，保留原密码和 `password_change_required`，不得恢复任何旧会话或隐式执行密码重置。首版停用请求不保存操作原因，审计仍记录操作者、目标、状态变化、结果、时间和 `requestId`。

管理员重置密码是独立安全动作，不得复用 `save` 或本人 `change-password`。该动作只允许以启用状态的普通非本人用户为目标；停用用户、系统内置用户和当前操作者本人必须拒绝，且重置不得隐式改变账号状态。后端生成满足密码策略的随机临时密码，并在同一事务中保存其摘要、设置 `password_change_required`、撤销目标用户全部会话、增加 `revision` 和记录审计。临时密码不设置独立时间期限，在用户完成强制改密或管理员再次重置前保持为当前有效密码。事务提交成功后仅在该次响应中返回一次临时明文密码，服务端不保存可恢复明文，也不提供再次读取接口；密码不得进入审计或日志。该动作实施前必须先加入 OpenAPI 和权限目录。

用户与角色启停共用读取、revision 检查、状态转换检查、CAS 写入及通用审计流程，使用原对象状态与 revision 和既有审计存储。输入校验后，在领域持有的授权更新锁与同一事务内，依次读取、检查 revision、检查状态转换、执行专有规则并原子提交；陈旧 revision 优先返回对象冲突，同状态请求不增加 revision、不写审计。通用审计记录领域、实体、对象、操作者、前后启用事实、前后 revision 与 requestId，保留 APP 事件名；专有规则、副作用或审计失败全部回滚。用户停用撤销全部会话，启用不复活；角色停用保留关联与会话。拼音复用后端纯转换工具；用户在创建和改名时维护检索列，角色按需计算并在分页前匹配。

### 5.6 角色管理

角色管理动作、路径与数据结构以 Hono 生成契约为准。

每条权限独立授权。菜单不依赖 `query` 权限，因此不得自动补授或强制依赖同实体的 `query`；每项操作只由其精确动作权限决定。

角色查询固定每页 20 条，默认包含启用及停用角色；在完整授权集合上对编码、真实拼音、名称做关键词 OR 包含匹配后，按 `code`、`id` 升序分页。原生摘要返回 `id/code/py/name/enabled/revision`；revision 为十进制字符串，启用事实显示为启用/停用。角色类型为 `NORMAL/SYSTEM/SUPERADMIN`（普通角色/系统角色/超级管理员）；动作完整集合为 `edit/enable/disable`（编辑/启用/停用）。查询和详情按操作者当前授权上限、自持角色和精确动作权限返回资格与 `assignable`。`system` 与 `superadmin` 可见但不可编辑启停。编辑器将动作资格与 get、save、权限目录 query 的实际依赖相交；单项 API 不额外要求其他读取授权。旧 status、状态筛选、排序与数字 revision 管理输入不再接受。

角色详情返回编码、拼音、名称、说明、启用事实、类型、完整权限资料、revision、创建和更新时间以及同一套动作与可分配结论。`superadmin` 的权限详情在读取时动态展开为全部启用权限，但数据库不保存逐项关联；普通有限权限集合无论当前是否恰好覆盖全部权限，都不得获得通配身份。

创建普通角色不接受客户端编码、拼音、启用事实或 revision；创建和保存必须提交非空且全部启用的完整权限集合。后端在授权更新锁和同一事务中分配 `ROL-0001` 至 `ROL-9999` 的最小下一个顺序编码，新角色立即启用；既有编码保持不可变。名称去除首尾空白后按英文大小写不敏感规则唯一，新写入不得与任何既有规范化名称冲突，迁移不得重命名或合并既有歧义数据。编号耗尽、名称重复、权限缺失、权限停用或权限超过操作者授权上限都返回稳定且脱敏的业务错误。编码分配、名称检查、角色、完整权限集合和审计原子提交。

保存只允许修改普通角色去除首尾空白后的唯一名称、可选说明和完整权限集合；编码和状态不可通过保存改变。后端在授权更新锁内重新计算操作者授权上限、目标当前权限、操作者角色关联和请求结果，拒绝系统或超级管理员角色、操作者自持角色、当前目标或请求结果超过授权上限、revision 冲突以及移除最后有效授权管理员。目标原有关联的停用权限保持可见，但保存请求不能继续包含停用权限，必须由管理员明确移除。

启用和停用使用稳定角色 ID 与 revision，分别要求精确动作权限，并在授权更新锁内重新验证目标可维护性、操作者关联、当前状态和最后有效授权管理员保护。停用只改变角色状态，不删除角色权限或用户角色关联，也不撤销现有会话；从关联用户下一次受保护请求开始，该角色不再贡献权限。重新启用后，从下一次请求开始只恢复仍启用权限的贡献。状态变更记录操作者、目标、结果、时间和 request ID，首版不保存原因。

### 5.7 权限目录

权限目录动作、路径与数据结构以 Hono 生成契约为准。

权限目录只公开目录查询和权限详情查询；权限创建、路由目录同步以及权限启停由部署流程或权限来源领域的受控流程负责，不得变成普通请求中的隐式行为。

权限详情中的“直接关联角色数”只统计 `app_role_permissions` 中对该权限的显式角色关联，且包含停用角色；不包含启用 `superadmin` 的动态通配结果。

### 5.8 系统参数

系统参数动作、路径与数据结构以 Hono 生成契约为准。

通用管理动作独立校验有效会话、CSRF 和对应精确路径权限；`get` 返回新鲜详情。参数键、名称、说明、类型、默认值和约束均不得由普通接口创建、删除或修改。`save` 与 `reset` 不得把修改前后的参数值写入审计摘要。

`POST /session/app/get` 是唯一的匿名启动展示接口，只返回企业名称等非敏感品牌展示资料，不返回参数键、默认值、约束、revision 或其他系统参数。它不接受查询条件，也不得扩展为通用公开配置接口。

## 6. 管理接口通用规则

分页、过滤和排序字段使用 OpenAPI 生成类型。

并发写请求必须携带目标当前 `revision`。更新 SQL 同时匹配 `id` 和 `revision`，成功后将 `revision` 加一；未更新任何行时重新判断“不存在”或“数据冲突”，禁止后写静默覆盖先写。

所有 ID、状态、分页范围、字符串长度和关联对象都必须在进入核心用例前校验。客户端字段名、排序方向和过滤表达式不得直接拼接 SQL。

## 7. 事务与一致性

以下操作必须使用单个数据库事务：

- 创建用户及分配初始角色；
- 替换用户角色集合；
- 创建或修改角色及替换权限集合；
- 停用用户并撤销其会话；
- 修改密码并撤销旧会话；
- 管理员重置密码并撤销目标用户全部会话；
- 创建、轮换或撤销会话与写入对应关键审计事件。
- 修改或恢复系统参数及写入对应审计事件。

授权关联变更成功提交后，权限缓存才能失效。若缓存失效失败，必须采用版本号校验或默认回源数据库，不能继续把旧权限作为有效授权。

新增领域权限的数据库基线只负责登记 `app_permissions`；不得再为 `superadmin` 逐项插入 `app_role_permissions`。普通角色仍通过显式关联授权。

## 8. 安全与审计

- 密码使用当前认可的自适应强哈希算法，并在配置中固定参数和升级策略；
- 登录接口实施失败计数和必要的临时锁定；独立的可部署一致登录限流不属于当前系统；
- Cookie 会话令牌、CSRF Token、密码和密码摘要禁止进入响应日志；
- 除认证入口以及本文明确列出的本人自助接口外，所有业务 `POST` 请求同时校验会话、CSRF 和精确 API 权限；
- 管理员不能停用最后一个可执行核心授权管理的有效账号，具体防锁死规则在初始化方案中固定；
- 审计记录至少包含事件类型、操作者、目标、结果、时间、`requestId` 和必要的变更摘要；
- 审计摘要不得包含密码、令牌、Cookie 或完整敏感数据；
- 权限不足与未登录使用不同的稳定业务码；内部异常不暴露 SQL、堆栈和数据库对象名。
- 统一业务响应包络为 `{code, errorKey, message, data, requestId}`。`code` 只表达未认证、无权限、校验、冲突和内部异常等大类；非零 `code` 必须同时返回稳定、扁平的 `errorKey`，前端按已知 `errorKey` 选择用户提示或业务分支，不比较、匹配或推断 `message`。未知 `errorKey` 使用经现有安全清理移除请求标识后的后端可读 `message`，空说明才按错误大类回退；成功响应的 `errorKey` 为空字符串。

## 9. 测试验收

至少覆盖：

1. 登录成功、统一失败消息、锁定、停用账号和密码变更后的旧会话失效；
2. Cookie 属性、会话到期、注销幂等、CSRF 校验，以及同一会话重复恢复和多标签页恢复时 Token 保持一致；
3. 登录和恢复只返回唯一会话上下文；多角色权限去重并集，以及用户、角色、权限停用后的即时失效；
4. 精确路径鉴权，拒绝前缀、大小写变化和通配符匹配；
5. `superadmin` 无逐项关联仍获得全部启用权限，新增和停用权限能即时反映在展开后的登录 `apiPaths` 数组；
6. 用户角色和角色权限批量替换的事务回滚；
7. 并发修改相同用户或角色时只允许一个版本成功；
8. 非 Session `apiPaths` 按 `domain/entity` 去重形成导航资源；仅有 `create` 的资源仍可见但不发查询，未登记资源明确未实现，直达与权限变化使用相同资源判定；
9. 所有管理接口均不返回或记录敏感字段；
10. 未登录、无权限、参数错误、数据冲突和内部异常映射到稳定业务错误类别；角色、用户并发修改等需要前端采取特定动作的冲突使用稳定 `errorKey`，修改英文诊断文字不得改变界面行为。

## 10. 已配置策略与待决事项

当前实现已经固定：

- 用户名在比较和保存前去除首尾空白并转为小写，长度为 3–64 个 Unicode 字符；
- 密码最小长度由 `APP_PASSWORD_MIN_LENGTH` 配置，默认 12、允许 8–128，实际密码最长 256 个字符，
  并且必须同时包含 ASCII 小写、大写、数字和符号；
- 登录和会话恢复响应返回当前生效的密码最小长度，供开户和本人改密界面使用同一策略边界；
- 连续失败锁定阈值和锁定时间分别由 `APP_SIGNIN_LOCK_THRESHOLD`、`APP_SIGNIN_LOCK_DURATION` 配置，
  默认 5 次和 15 分钟；
- 会话空闲和绝对有效期分别由 `APP_SESSION_IDLE_TIMEOUT`、`APP_SESSION_ABSOLUTE_TIMEOUT` 配置，
  默认 30 分钟和 12 小时；受保护请求延长空闲期限，但不得突破绝对期限。

仍待产品或安全方案明确：

- 用户名允许字符、国际化用户名及保留名称策略；
- 单用户最大并发会话数；
- 账号恢复流程；
- 是否引入组织、岗位、租户和数据范围授权；
- 审计数据保留期限和查询权限。

## 11. 业务协作

### 工作台待办

工作台通过会话级 `POST /app/workbench/query` 聚合当前用户可处理的业务资料与业务单据。该接口不新增独立权限；后端必须从当前会话权限推导实体范围，不接受调用方指定实体或动作集合。

- 目标 Workbench Pending Stage 只有 `APPROVE`：Draft 是当前页面实例的临时编辑状态，不进入服务器工作台。它不是 Approval Status；每行“状态”只显示真实的 `PENDING` 或 `REJECTED` Approval Status。
- 待批准 Submission 只在拥有该资源提交查询权限（BOB/WFL 为 `submission-query`，VOU 为 `query`）且中央 [Approval Action Availability](approval.md#32-approval-action-availability) 返回 `reject`、`approve` 或 `unreject` 至少一项时进入 `APPROVE`。`APPROVED` 不产生工作台人工待办。
- 聚合响应只返回列表摘要和当前会话动作快照。APP 只组合 `view`、`edit`、`delete` 等资源动作，`reject`、`approve`、`unreject`、`unapprove` 生命周期动作必须原样来自中央 Approval 的确定顺序，不能在 APP 或前端按状态、提交人或权限再次推断。
- 版本化资料提交详情必须通过 BOB/WFL 对应 `submission-get` 读取，当前正式档案浏览才使用 BOB `get`，单据详情使用 VOU `get`；正向和反向处理调用行所属 BOB/WFL/VOU 动作接口。ACC Mapping 与 RPT Definition 不进入审批工作台；WFL Definition 及仍登记的版本化实体使用自身可执行契约，不得按展示分类改路由。
- 强类型业务档案待办显示该 candidate 自己的名称；Customer 的账户变更只产生一个 Customer 待办，不产生账户独立待办。名称缺失时回退显示档案编码。
- 列表按更新时间倒序进行服务端分页；关键词只匹配资料编码/名称或单据号/往来方。
- 资料和单据均可按实体类型与待办状态进行服务端筛选；客户端提交的实体筛选只用于缩小结果集，后端仍必须先按当前会话权限推导可见实体并取交集，不能将筛选值视为权限范围。

待办行的生命周期动作限定为仍处于待办状态的直接流转。`reject` 要求非空 reason；`approve` 与 `unreject` 不要求也不接受 reason。界面“撤回”是目标 Domain 的开放 Submission 删除资源动作，不是 lifecycle status 或 `unsubmit`。BOB、WFL 和 VOU 的 `APPROVED` 不属于待办，不为提供 `unapprove` 而进入工作台；AUX、ACC 映射与 RPT 定义不产生 Approval 待办，也不提供 lifecycle 动作。

`availableActions` 是查询快照而不是授权凭证。目标 BOB/WFL/VOU 动作接口仍重新校验会话、精确权限、Approval 状态、revision、职责分离和既有 Domain blocker；成功或失败后客户端都刷新当前页，revision、状态或权限冲突不得自动重试。

### 权限变更与会话一致性

- 用户角色或角色权限变更后，后端必须确保后续请求使用最新权限。
- Session 恢复或权限版本失效后必须重新得到 `apiPaths`；权限被撤销后后端必须立即拒绝无权限 API 请求，前端同步移除对应 Navigation Entry 与已挂载资源实例。
