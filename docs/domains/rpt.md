# RPT 报表领域

## 1. 目标与边界

RPT（Reporting）负责定义、验证、执行和导出面向用户的查询报表。它读取其他领域已经形成的事实，不拥有或改写客户、供应商、单据、会计分录、库存数量、核算对象等业务事实。

RPT 拥有：

- 报表定义、不可变报表版本及其结果列契约；
- 报表版本的 SQL 安全校验、批准和当前有效性；
- 按报表独立授权的查询、分页和导出执行；
- 报表中心及按稳定编码打开报表的通用页面；
- 首次批准时与 APP 原子注册报表精确权限的协作规则。

RPT 不拥有：

- ACC 的科目、分录、余额、库存数量或成本事实；
- VOU、BOB、AUX 或核算对象的业务生命周期；
- ACC 查询能力、报表投影、只读视图或第二套业务事实；
- 独立的角色权限体系、用户账簿分配或执行层追加账簿过滤；
- 为每张报表建立独立主导航入口。

HTTP 业务接口使用 `POST application/json`、统一响应包络和 `/rpt/{report}/{action}` 前缀。具体实体、字段和响应以 OpenAPI 为唯一线协议来源。

## 2. 首批报表

所有报表统一由报表定义和版本机制提供。首批预置报表 SQL 可以直接读取各领域内部数据表，不经 ACC 查询接口，也不建立报表投影或只读视图。

### 2.1 科目流水与科目余额

科目流水按报表定义声明的账簿、科目、辅助核算维度、币种和日期范围展示会计事实；科目余额按同一口径汇总借贷发生额和余额。ACC 仍只保存事实，RPT 负责面向用户的查询和导出。

### 2.2 应收预收与应付预付

应收预收、应付预付分别按账簿、往来单位、币种和截止日展示原额与净额，并按到期日和先进先出倒推未结金额及账龄。报表必须区分应收与预收、应付与预付，不把不同方向抵销成无法解释的单一余额。

### 2.3 库存

库存报表按账簿、库存科目、仓库、产品和截止日展示期初、入库、出库、期末数量、移动平均单价和金额，并支持下钻到来源 VOU。库存金额和成本口径直接取对应会计账簿的库存数量及成本事实。

### 2.4 票据

票据报表合并全局票据身份及状态与所选账簿的资产或负债方向和会计金额。全局身份和状态不因账簿查询而复制；账簿金额仍按所选账簿独立展示。

### 2.5 空桶

空桶报表按客户、桶型和截止日展示期初、发出、收回、调整和欠桶余额；配置金额核算时同时展示金额。数量状态取全局空桶事实，金额取所选会计账簿的独立价值。

### 2.6 员工借款

员工借款报表按账簿、员工、币种和截止日展示借款、还款、费用核销、余额及先进先出账龄。余额为负时必须明确标识为应付员工，而不是继续显示为员工借款。

## 3. 报表定义与版本

报表定义至少包含：

- 首次批准前可维护、首次批准后不可修改的稳定编码；
- 名称和说明；
- 一个或多个不可变报表版本；
- 当前生效版本（可以为空）以及停用标志；
- 查询和导出精确权限的 APP 注册状态。

报表版本包含版本号、SQL、类型化绑定参数和结果列契约。版本状态为 `DRAFT` 或 `APPROVED`，审批状态与当前有效性分离：有效性为 `VALID` 或 `INVALID`。

- 草稿可以保存和继续校验；
- 修改已批准版本必须创建新版本，不能原地编辑；
- 批准新版本时原子切换当前生效版本；
- 历史版本只用于审计或复制为新草稿，不能直接重新生效；
- 首次批准后稳定编码永久冻结；曾批准的报表只能停用，不能删除；
- 报表没有生效版本时仍保留定义、版本历史、角色关联和审计记录。

报表定义可以从空白创建；创建时提交稳定编码、名称和首个草稿版本。首次批准前可以继续编辑定义和草稿，首次批准后稳定编码永久冻结。

## 4. 查询 SQL 安全

报表 SQL 必须是单条只读查询：只允许单条 `SELECT` 或 `WITH ... SELECT`，由数据库只读角色在只读事务中执行。禁止字符串拼接、多语句、写入、DDL、可写函数以及绕过只读角色的执行路径。

预置报表 SQL 直接依赖预置科目编码。用户修改科目编码后，必须同步修改受影响的报表 SQL；RPT 不维护科目到报表项目的映射，也不为旧表或字段保留兼容视图。

查询强制分页，每页最多 100 条；导出最多 100,000 条。查询和导出均设置数据库执行超时、只读事务和资源限制，超时等瞬时运行故障不改变报表版本有效性。

## 5. 参数与结果契约

首版绑定参数类型固定为：`TEXT`、`INTEGER`、`DECIMAL`、`BOOLEAN`、`DATE`、`DATE_RANGE`、`ENUM` 和受控 `REFERENCE`。引用选择器只开放会计账簿、会计科目、客户、供应商、其他单位、员工、部门、产品、仓库、资金账户、资产和票据；执行时只绑定稳定 ID，不把用户可编辑名称拼入 SQL。

每个报表版本必须显式声明结果列契约。每列至少声明 SQL 别名、业务显示名、顺序、数据类型、宽度、默认可见性和格式。批准时实际返回列必须与契约完全一致；通用页面和导出均只按该版本的列契约展示结果。SQL 可以返回任意业务列，但不得让页面或导出自行猜测列含义。

## 6. 批准、执行与有效性

报表版本批准前必须完成全部校验：

1. 解析 SQL，确认只有一条允许的只读查询；
2. 确认参数占位符与类型声明完全匹配；
3. 在只读角色下执行 `PREPARE` 和不带 `ANALYZE` 的 `EXPLAIN`；
4. 使用审批人提供的验证参数，在只读事务、短超时和限量结果集内试跑；
5. 确认实际返回列与结果列契约完全一致。

任一步失败都不得批准。已批准版本后来遇到未定义表、列、函数或类型不匹配等确定性的 SQL 结构错误时，必须标记为 `INVALID`，停止执行并停用该报表的 `query`、`export` 权限；审批历史、角色关联和审计记录继续保留。连接失败、超时等瞬时故障只返回运行错误，不改变有效性。

RPT 不继续重复执行已知无效 SQL，也不自动回退历史版本。恢复只能通过批准一个重新验证过的新版本；批准新的有效版本后重新启用权限并恢复原有角色授权。

## 7. 权限与 APP 协作

报表定义的查看、保存、批准和反批准是统一的高权限管理动作；使用者的查询和导出按报表分别授权。查询权限不自动包含导出权限，导出权限也不授予报表管理能力。

报表首次批准时，RPT 与 APP 在同一事务中以报表稳定编码注册精确的 `query`、`export` 权限。草稿不创建使用权限。首次批准后启用权限；反批准或停用使报表没有生效版本时停用两项权限，但保留既有角色关联；重新批准后重新启用并恢复原授权。RPT 不建立第二套角色权限体系。

报表访问权有意不继承 ACC 的用户账簿分配范围。获得某张报表的查询或导出权限，即可读取该报表定义返回的全部数据，包括跨账簿数据。报表 SQL 维护人员负责在定义中实现所需数据范围，RPT 执行层不追加账簿过滤；授予报表权限必须被视为独立的数据访问决策。

## 8. 报表中心与前端

所有报表统一进入报表中心。前端使用一个固定的通用页面展示用户已获权报表，并支持按报表稳定编码深链接；不为每张报表创建独立主导航入口，也不根据报表定义动态生成未经授权的菜单。

通用页面按当前生效版本的结果列契约展示分页结果和导出结果。无生效版本或版本为 `INVALID` 时，页面不提供查询或导出，并明确显示报表当前不可用的业务原因。

## 9. 数据库结构变更与发布门禁

涉及数据库结构的发布必须在迁移事务提交前，基于迁移后的结构重新验证全部当前 `VALID` 报表。任一报表不兼容就回滚迁移并阻断发布。

继续发布前，必须在同次变更中提供并批准兼容的新报表版本，或由管理员事先明确停用受影响报表。不得为旧表或字段保留兼容视图、别名、fallback 或第二套查询口径。

## 10. 验收边界

至少覆盖：

1. 预置报表和空白创建报表均能按稳定编码管理；
2. DRAFT、APPROVED、VALID、INVALID 的状态分离及不可变版本；
3. 参数声明、结果列契约、`PREPARE`、`EXPLAIN` 和限量试跑的批准门禁；
4. 单条只读 SQL、只读角色、事务、超时、分页和导出上限；
5. 查询与导出独立授权，APP 首次批准原子注册权限，反批准/停用保留角色关联；
6. 报表权限跨账簿且不继承 ACC 账簿分配，SQL 维护人员负责数据范围；
7. 报表中心通用页面、稳定编码深链接和动态结果列契约；
8. 确定性结构错误停用权限、不重复执行、不回退历史版本；
9. 数据库迁移前验证全部当前有效报表，不兼容时回滚阻断；
10. 科目流水、科目余额、应收预收、应付预付、库存、票据、空桶和员工借款首批报表口径。
