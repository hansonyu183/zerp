# 测试与发布流程指标

流程优化使用 GitHub 已有 PR 和 Actions 事实做基线，不新增制品注册表，也不把运行结果提交到仓库。只读命令：

```bash
scripts/release-metrics.sh
```

默认统计最近 20 个已合并 PR，并输出 JSON。`ZERP_RELEASE_METRICS_LIMIT` 可以调整样本数，`ZERP_GITHUB_REPOSITORY` 可以覆盖仓库名。

## 指标定义

- `repeat_validations`：同一 PR 的 `Full-stack quality` 工作流运行次数减一。已取消运行计入重复次数，但不计入机器执行时长。
- `system_seconds`：同一 PR 所有未取消 `Full-stack quality` 工作流的运行时长总和，用于反映重复执行和慢门禁共同消耗的系统时间。
- `flow_seconds`：PR 从创建到合并的自然时间，用于反映等待检查、Review、预览和人工确认的完整流转时间。
- P50 和 P95 采用 nearest-rank 百分位；样本按合并时间倒序取最近 20 个。

GitHub Actions 在分支删除后可能不再返回工作流到 PR 的直接关联，因此脚本优先使用 API 的 PR 关联，并以 PR head 分支和创建至合并时间窗补充关联。分支名复用会污染历史指标，开发分支必须保持唯一命名。

## 迁移前基线与目标

2026-08-08 在切换直连 `main` 前采集的最近 20 个合并 PR 基线：

| 指标             | 基线                   | 第一阶段目标 |
| ---------------- | ---------------------- | ------------ |
| 重复验证总次数   | 102                    | 降低至少 50% |
| 系统时间 P50     | 767 秒                 | 降低至少 30% |
| 系统时间 P95     | 3273 秒                | 观察项       |
| 完整流转时间 P50 | 1943 秒                | 观察项       |
| 完整流转时间 P95 | 21109 秒，约 5.86 小时 | 降低至少 20% |

每完成 20 个直连 `main` 的 PR 后重新运行同一命令，并与这组基线比较。若重复验证达到目标但 P95 流转时间没有改善，应分别检查 Review 等待、固定预览锁等待和外部发布入口，而不是删减必需门禁。
