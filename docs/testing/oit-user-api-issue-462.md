# OIT 用户承接：ZERP 公开 API 核查

此记录对应 [oit-zerp #21](https://github.com/hansonyu183/oit-zerp/issues/21)、[ZERP #462](https://github.com/hansonyu183/zerp/issues/462)。依据 `10bc34656404fceb70e9ebe0a9c5158faa0cd58d` 的 Hono/Zod 契约、领域服务和权威领域规则核查。旧版直接写目标库的用户试迁不构成本次 Go/API 验收。

## 现有入口与 #2 规则

所有正式业务动作使用 `POST application/json`、Session Cookie、CSRF Token 和精确路径权限，返回 `{code,errorKey,message,data,requestId}`。`requestId` 只用于追踪，不保证去重或结果恢复；成功响应中的 `data` 才是业务结果。响应结构以 [APP 契约](../../apps/api/src/app/independent-contract.ts)、[AUX 契约](../../apps/api/src/app/aux-contract.ts)及 [ACC 契约](../../apps/api/src/acc/contract.ts)为准。

| 对象           | 当前创建、查询、变更入口                                                                                          | 授权与并发                                                                                                        | 对 #2 的核查结果                                                                                                                                                                                                       |
| -------------- | ----------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 账号           | `/app/user/create`, `/app/user/query`, `/app/user/get`, `/app/user/save`, `/app/user/enable`, `/app/user/disable` | 各入口有精确权限；角色委派在授权锁内检查上限，保存及启停检查十进制字符串 revision；账号编码规范化后唯一           | 账号可独立于员工。现行创建必启用且角色非空，不能直接承接来源停用或无角色待授权账号；不得用创建后立即停用规避。创建结果未知时，可按不可变、唯一账号编码查询并精确核对，不可按姓名认领。                                 |
| 角色           | `/app/role/create`, `/app/role/query`, `/app/role/get`, `/app/role/save`, `/app/role/enable`, `/app/role/disable` | 各入口有精确权限；权限集合受操作者授权上限约束；保存、启停检查 revision；角色名规范化后唯一，角色编码由服务端分配 | 不能复制 OIT 角色字母或菜单权限，目标角色与权限须逐项审核。角色名可改，且由服务端分配 ID；创建响应丢失时不能仅凭同名认领，需稳定目标 ID 或可验证的幂等依据。                                                           |
| 部门、岗位     | `/aux/{department\|position}/{create,query,get,save,enable,disable}`                                              | 各动作精确权限；保存、启停检查 revision；创建由服务端生成 ID 和编码，默认启用                                     | 只能承接真实必要层级及岗位；不按重名合并。名称并非唯一身份，当前创建响应丢失无法可靠找回。                                                                                                                             |
| 员工           | `/aux/employee/{create,query,get,save,enable,disable}`                                                            | 与 AUX 相同；可不填法定识别号、任职日期、类别、部门、岗位及任职主体                                               | 不必补造身份或雇佣资料；无账号员工可独立存在。但创建默认启用，且 APP 关联新员工时要求员工启用，来源停用员工与账号关联仍有缺口。员工姓名和可空法定识别号不能作为自动认领键。                                            |
| 账簿与人员范围 | `/acc/book/query`, `/acc/book/get`, `/acc/book/save`                                                              | 精确动作权限和账簿查询/操作范围同时生效；完整人员集合与其他账簿资料一起由 `expectedRevision` 在同一事务保存       | 查询、操作分别授权，空来源范围不代表全员。整组保存能因账簿 revision 变化而拒绝并发覆盖；现行保存只允许启用用户入范围，无法在账号启用前预置范围。操作者既有范围被保留，客户端须按返回集合核对，不能把它误认为来源授权。 |

`/session/auth/signin` 在用户停用时拒绝登录；启用用户即使没有角色也可能建立仅能改密的会话，因此“待授权不可登录”必须依靠账号停用事实。员工的启停不授予或撤销 APP 会话权限。普通资料及角色操作仍需遵守 APP 授权上限与最后有效管理员保护。

## 未知结果与目标基线

- `/app/user/create` 可在独占目标预先证明账号编码未占用；发送后失去响应时，按编码查询并回读不变字段和角色/员工关联。已存在且不属于本批次的同编码账号不得认领。`/app/user/save`、启停及角色授权使用 revision，未知结果先回读，核对目标状态和审计后决定继续或停止。
- 角色创建、部门/岗位/员工创建目前缺少可在发送前封存并按 ID 回读的目标身份。`query` 的模糊匹配、分页及可重复名称不足以恢复；这些入口必须阻断，直至正常 API 提供可靠身份或幂等保证。
- `/acc/book/save` 是整组替换。客户端必须在发送前封存账簿 ID、原 revision、原完整人员集合与预期集合，只增加经 #2 审核的 `ACC-0001` 权限；响应未知时用 `/acc/book/get` 比较 revision 和完整集合。其他并发修改即使导致同一预期 revision 冲突，也不能静默覆盖。
- `/healthz` 和 `/readyz` 仅返回 `status`；当前 Session Context 也没有目标数据实例身份。相同 URL 或 API 程序版本不能证明数据库未重建。批次映射复用前需要受支持、重建会改变的目标基线身份；备份、重建和初始化仍由 ZERP 运维流程执行。

以上是现状与缺口，不宣告 #21 可供 #22 用户试迁。隔离环境真实 HTTP、运行源码 SHA、目标重建识别以及未知结果故障验证将在能力补齐后记录于此。

## 本次目标侧调整与 Go 客户端契约

以下能力在此任务的候选代码中实现，均走正常 APP、AUX 或 ACC 领域服务；源 OIT 身份和批次映射仍由 `oit-zerp` 持有。

| 入口                                                     | 新输入或输出                                                                                                                  | 响应未知时的处理                                                                                                                                                     |
| -------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/session/auth/signin`、`/session/auth/restore`          | 成功 `data.targetId` 为当前数据库初始化身份 UUID；同一目标稳定，新建目标变化                                                  | 每次恢复会话核对封存的 `targetId`；不同即停止旧批次。备份恢复可保留原身份，仍需核对备份截止状态。                                                                    |
| `/app/role/create`                                       | 可选 `id` 为 26 位 ULID，原有名称、说明、完整权限集合仍由正常规则校验，角色编码仍由服务端生成                                 | 发送前封存 ID；结果未知时 `/app/role/get` 按 ID 回读权限及名称。重复 ID 返回 `conflict`，不自动认领。                                                                |
| `/app/user/create`、`/app/user/save`、`/app/user/enable` | 创建可传 `enabled:false` 并使用空 `roleIds`；默认仍启用且必须带角色。停用账号可保存空角色，启用时必须已有至少一个当前启用角色 | 先停用建档和核对，再审核角色并保存，最后显式启用。停用期间登录返回 `account_disabled`；创建响应未知时按预封存的唯一账号编码查询并精确核对，保存和启用使用 revision。 |
| `/aux/{department,position,employee}/create`             | 可选 `id` 为 26 位 ULID；`employee` 另可传 `enabled:false`，缺省仍启用。部门和岗位的输入、编码、引用校验不变                  | 发送前封存 ID；结果未知时所属实体 `/get` 按 ID 回读全部资料和启用事实。重复 ID 返回 `conflict`；名称和法定识别号不作为自动认领依据。                                 |
| `/app/user/create`、`/app/user/save`                     | 员工关联可指向真实但已停用的 AUX 员工 stable ID；关联不启用员工，也不单独授予登录或业务权限                                   | 回读用户详情核对精确 `employeeId`、角色与 revision。                                                                                                                 |
| `/acc/book/save`                                         | 完整 `queryUserIds` 和 `operateUserIds` 可含已存在的停用账号；账号停用期间没有有效会话                                        | 保留原 `expectedRevision` 和完整范围，未知结果先 `/acc/book/get` 核对 revision 与两个集合；存在其他修改时阻断，不用重读后的 revision 自动覆盖。                      |

`X-ZERP-Model-Build: zerp-model-0.4.0` 是当前 APP/Session 路由要求的客户端模型头，不代表目标数据身份。所有业务写入仍需登录 Cookie 和 `X-CSRF-Token`。AUX 和角色 create 的 ID 为目标 stable ID，须在来源批次私有工件中发送前确定并封存；`requestId` 不作幂等键。

隔离 PostgreSQL 的真实 HTTP 集成测试覆盖角色与部门指定 ID 创建、回读、重复 ID 冲突、停用员工创建与回读、账号保留停用员工关联，以及登录/恢复返回同一目标身份。APP 真实 HTTP 测试覆盖停用零角色创建、登录拒绝、零角色启用拒绝、授权后显式启用和启用账号不可清空角色。ACC 服务和 HTTP 路由测试覆盖停用账号预置两个独立范围和陈旧 revision 拒绝。

## #22 试迁发现的本人关联查询

真实迁入账号 `kj01` 可登录、首次改密、重新登录并读取本人资料，但其受审会计角色没有 `/aux/employee/get` 权限。本人查询关联员工的 stable ID 应由 `/session/user/get` 返回只读 `employeeId`，`/session/user/save` 回传同一字段；该字段仅取当前账号的现有员工关联，可为 `null`，不开放员工档案或修改权限。隔离 PostgreSQL 的真实 HTTP 集成测试覆盖停用员工关联账号在本人改密后回读同一 `employeeId`。`oit-zerp` 的 Go 验收据此核对本人资料、员工关联及原有越权拒绝。
